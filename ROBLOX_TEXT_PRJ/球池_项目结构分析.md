## 一、项目总览

这是一个 **球池收集 / 吸附小游戏原型**:场景中央有一个装满 4 色小球的球池,玩家手持对应颜色的工具(Tool)靠近后会自动吸附同色球,每把工具最多收集 **25** 颗;收集满后走到球池外对应颜色的站台旁按 **E**,球会逐颗飞向站台堆叠展示。

整个项目由 **1 个配置模块 + 1 个服务器脚本 + 1 个客户端脚本** 驱动,UI 全部由客户端脚本动态生成(StarterGui 为空),没有使用 DataStore 持久化。

## 三、服务(Service)使用分析

项目中真正被**代码引用**的 Roblox 服务如下:

| 服务 | 位置 | 用途 |
|---|---|---|
| `ReplicatedStorage` | 服务器 + 客户端 | 存放共享配置与 RemoteEvent |
| `RunService` | 服务器 + 客户端 | `Heartbeat` 驱动球的飞行推进、客户端扫描计时 |
| `Players` | 服务器 | 管理玩家数据初始化 / 清理 |
| `ProximityPromptService` | 服务器 | 监听站台 `PromptTriggered` 触发存放 |
| `TweenService` | 服务器 | 已引用但代码中未实际调用 |
| `Workspace` | 客户端 | `GetPartBoundsInRadius` 做球体范围检测 |

空置/未启用的容器:`ServerStorage`、`StarterGui`、`Teams`、`SoundService`、`StarterCharacterScripts` 均为空;`StarterGui` 无任何元素,说明界面完全由客户端脚本运行时生成。

未接入任何后端能力(无 `DataStoreService` 存档、无 `TeleportService`、无 `HttpService` 调用)。

## 四、代码分析

### 1. `SuctionConfig`(配置模块,71 行)

客户端与服务器共用的唯一配置源,关键参数:

| 参数 | 值 | 含义 |
|---|---|---|
| `SUCTION_RADIUS` | 20 | 吸附检测半径(stud),**偏大**(大于整个 12×12 池体) |
| `SUCTION_SPEED` | 28 | 球被吸向 Handle 的速度 |
| `COLLECT_DISTANCE` | 0.7 | 判定"收集成功"的临界距离 |
| `COLLECT_COOLDOWN` | 0.5s | 两次收集的最小间隔 |
| `TOOL_CAPACITY` | 25 | 每把工具容量上限 |
| `DEPOSIT_RADIUS` | 5 | 站台可交互半径 |
| `DEPOSIT_SPEED` | 40 | 存放时球飞向站台的速度 |
| `DEPOSIT_STAGGER` | 0.06s | 存放时逐颗起飞的间隔 |
| `SCAN_INTERVAL` | 0.08s | 客户端扫描间隔 |
| `MAX_SUCTION_BATCH` | 1 | 每次扫描最多发起 1 个请求 |

还定义了映射表:`TOOL_COLORS`(工具名→颜色)、`STATION_COLORS`(站台名→颜色)、`COLOR_VALUES`(颜色→Color3),以及属性名常量 `BALL_COLOR_ATTR="BallColor"`、`TOOL_COLOR_ATTR="ToolColor"`。

### 2. `SuctionServer`(服务器脚本,327 行)— v7 架构

职责分四块:

- **收集**:客户端 `RequestSuction` 触发后,服务端做多重校验(球是 BasePart、有 `BallColor` 属性、未被标记 `Collecting`、未隐藏、颜色匹配、距离合法、玩家无在途球、该色未满 25),随后将球锚定(`Anchored=true`、`CanCollide=false`)并写入 `suctioning` 表,由 `Heartbeat` 驱动直线飞向 Handle 中心。
- **收集成功**:球到达 `COLLECT_DISTANCE` 后进入冷却等待,冷却结束执行 `doCollect`——球隐藏(Transparency=1)并瞬移到隐藏点 `(0,-500,0)`,按玩家×颜色存入 `collected` 表,计数+1,广播 `SyncSuction` + `PlayCollectSound` + `UpdateCollectUI`。
- **存放**:`ProximityPromptService.PromptTriggered` 触发(注意事件签名为 `prompt` 在前),校验站台→颜色映射后,把该玩家该色的球逐颗取出,先移出球池到运行时创建的 `DepositedBalls` 文件夹(防止客户端再次吸附),恢复可见,再按 0.06s 间隔延迟起飞飞向站台,按 `idx%5 / floor(idx/5)` 计算偏移在站台上方堆叠;全部结束后清零计数、更新站台 `StoredCount` 属性并广播 UI。
- **生命周期**:`PlayerAdded` 初始化 4 色数据并监听 `CharacterAdded` 同步 UI;`PlayerRemoving` 清理。启动时打印 `[SuctionServer] 已启动 v7`。

### 3. `SuctionClient`(本地脚本,192 行)

职责四块:

- **工具轮询**:每 0.1s 轮询角色身上装备的 Tool,根据其 `ToolColor` 属性更新 UI 计数显示。
- **UI(运行时生成)**:在 PlayerGui 创建 `CollectCountUI` 的 ScreenGui,顶部居中半透明圆角底衬(`Bg` Frame + UICorner),内含左侧颜色圆点(`ColorDot`)与计数文本 `x/25`(`GothamBold 28`)。`ResetOnSpawn=false` 保证重生不清除。
- **吸附检测**:以 Handle 中心为圆心,`GetPartBoundsInRadius(handlePos, 20, OverlapParams)` 且 **FilterDescendantsInstances 仅含 BallPool**——即只扫描球池内的球,保证已存放到池外的展示球不会被回收。每 0.08s 一次,命中同色可见未在途的球就 `FireServer` 请求吸附(本地满容量也会拦截,双保险)。
- **音效**:创建 `Sound`(rbxassetid://128062463831151,音量 0.5);收到 `PlayCollectSound` 就 Stop+Play 重播。同时监听 `SyncSuction` 把服务器标记的球立即隐藏。

## 五、网络通信(Remote)数据流

```
[客户端]                             [服务器]
   │ 扫描到同色球                        │
   ├─ RequestSuction(ball,pos,color) ──► │  校验(玩家/球/颜色/容量/在途)
   │                                    │  标记 Collecting, 加入飞行表
   │                                    ├─ SyncSuction(ball) ──► 所有客户端隐藏该球
   │                                    ├─ PlayCollectSound ───► 该客户端播音效
   │                                    ├─ UpdateCollectUI(color,count,25) ──► 客户端刷新计数
   │ 按 E 触发站台 Prompt                │
   ├───────────────────────────────────► │  PromptTriggered → 逐颗放球回站台堆叠
   │                                    ├─ UpdateCollectUI(color,0,25) ──► 清零显示
```

> ⚠ 发现:`SuctionRemotes` 中声明了 **`FrameMoved`** 与 **`DepositRequest`** 两个 RemoteEvent,但三个脚本均未引用(存放走的是 `ProximityPromptService`,不是 `DepositRequest`),属于**遗留死资源**。

## 八、观察与提示(供参考)

1. **无持久化**:收集进度只存在服务器内存,`Players.PlayerRemoving` 直接 `cleanupPlayer` 清空,玩家退出即丢失;服务器重启后球池归位、站台 `StoredCount` 不保留。
2. **`SUCTION_RADIUS=20` 偏大**:池体只有 12×12,20 stud 意味着玩家站在池边就能吸附整个池面,吸附缺乏"距离梯度"的挑战性。
3. **客户端可能高频请求**:`SCAN_INTERVAL=0.08s` 时每帧附近有可吸球就会 `FireServer`,虽有服务器 0.5s 冷却 + 在途拦截兜底,仍会产生较多无效请求;实际每玩家约 6~12 次/秒。
4. **双保险容量**:客户端与服务器各自校验 `TOOL_CAPACITY`,符合安全习惯;但吸附/存放均未做**颜色越权以外的其他利用防护**,Remote 均未限制频率(在途与冷却已限制基本节奏)。
5. **两个死 Remote**(FrameMoved / DepositRequest)可按需清理。
6. 存放动画机制设计合理:球先移出 `BallPool` 容器再可见,从而规避客户端只扫描球池的过滤逻辑,避免"回收已展示球"。
